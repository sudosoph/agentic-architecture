**TL;DR.** A Framework 16 with a Ryzen AI 9 HX 370, Radeon RX 7700S, and 96GB of DDR5 runs GLM-4 9B at Q8_0 at **28.4 tokens/sec** under ROCm 7.3, with a 90GB GART carve-out feeding the iGPU directly out of system RAM. That number is not a benchmark trophy. It is the threshold at which agentic loops stop being a budgeting problem and start being an architecture problem — which is a much better problem to have.

This post is the case for why 96GB of unified memory, not 64 and not 128, is the inflection point for solo builders running serious agentic workloads in 2026. It covers the hardware, the ROCm setup, the actual benchmark methodology, and the cost math against the frontier APIs.

## The thesis in one paragraph

If you are running multi-agent loops — planner → researcher → critic → executor, looped with retries — you cannot do it on metered cloud APIs at scale unless you have already raised money. A reasonably busy agentic dev loop today burns 5–20M tokens a day. At Claude Sonnet 4 prices, that's $15–$60. At GPT-5 reasoning prices, multiply that. Per developer, per day. Multiply by a team. Multiply by the experiments you don't run because you flinched at the bill.

96GB of system RAM, with most of it pinned as GART for an iGPU/dGPU pair that ROCm 7.3 finally treats as first-class, removes the budgeting layer. You stop asking *"can I afford to let this agent retry?"* and start asking *"is the loop converging?"* — which is the only question that actually matters.

## The hardware

This is what's under the keyboard right now:

```
Mainboard:  Framework 16 (AMD)
SoC:        AMD Ryzen AI 9 HX 370 (Strix Point, Zen 5 + RDNA 3.5 + XDNA 2)
dGPU:       Radeon RX 7700S (Navi 33, 8GB GDDR6)
Memory:     96GB DDR5-5600 (2 × 48GB SO-DIMM)
Storage:    2TB NVMe (Gen 4)
OS:         Ubuntu 24.04, kernel 6.11
```

A few notes on each line, because all of them are load-bearing:

**Strix Point's iGPU (Radeon 890M, RDNA 3.5)** is the actual workhorse for sustained inference under 12B params. It's tied to system RAM, which is the whole point. The dGPU is for bursty workloads — the cold start of a 13B model, image generation, occasional finetuning runs.

**96GB, not 64, not 128.** 64GB hits a wall the moment you want to keep a 9B model resident, run a context window over 32k, *and* leave headroom for VS Code + Chrome + n8n + a vector DB. 128GB exists as a Framework 16 option, but only as 2 × 64GB DDR5-5200 — slower, and the marginal $400 buys you tokens you will never spend on inference. You get more value buying a second NVMe and offloading swap there.

**Ubuntu 24.04 kernel 6.11.** ROCm 7.3 builds cleanly here. Kernel 6.8 (the 24.04 GA kernel) needs the HWE stack to get DKMS happy with the AMDGPU driver for Strix Point — not hard, but a tripwire. Just install the OEM kernel and stop.

## The 90GB GART trick

GART (Graphics Aperture Remapping Table) is the mechanism by which the iGPU sees system RAM as if it were VRAM. By default, Ubuntu hands the iGPU something miserable like 4GB of GART. To run a 9B model at Q8_0 (~9.5GB on disk, more in memory with the KV cache) you need GART to be much larger.

The setting is in `/etc/default/grub` as a kernel parameter:

```
GRUB_CMDLINE_LINUX_DEFAULT="quiet splash amdgpu.gttsize=92160"
```

`gttsize` is in MB. 92160MB = 90GB. Then:

```bash
sudo update-grub && sudo reboot
```

After the reboot, `glxinfo -B` should report the new GTT size, and `rocm-smi --showmeminfo vram` will show the iGPU now has the headroom you actually paid for. This is the single config change that does the most work in this entire stack.

Leave 6GB of system RAM unmapped from GART — that's your floor for the OS, your editor, and the chrome tabs you are about to ignore for the next three hours.

## The ROCm 7.3 install (the part that used to be painful)

ROCm 7.3 is the first release where I would call Strix Point + RDNA 3.5 a supported configuration instead of a science project. Earlier 7.x releases shipped HIP runtimes that crashed on `gfx1150` (the iGPU's ISA code) under any meaningful load. The 7.3 packages handle it. Install via the official APT repo:

```bash
sudo apt update
sudo apt install python3-setuptools python3-wheel
wget https://repo.radeon.com/amdgpu-install/7.3/ubuntu/noble/amdgpu-install_7.3.x_all.deb
sudo apt install ./amdgpu-install_7.3.x_all.deb
sudo amdgpu-install -y --usecase=rocm
sudo usermod -aG render,video $USER
```

Reboot. Then verify:

```bash
rocm-smi
rocminfo | grep gfx
# expected: gfx1150 (iGPU), gfx1102 (RX 7700S)
```

If `rocminfo` lists both `gfx1150` and `gfx1102`, you have a working pair. The HIP runtime can target either, and llama.cpp will pick whichever you point `HIP_VISIBLE_DEVICES` at.

## Building llama.cpp for HIP

llama.cpp's HIP backend has been stable on RDNA 3 for a year and on RDNA 3.5 since around February 2026. Build it directly — the prebuilt binaries from the releases page miss the `gfx1150` target.

```bash
git clone https://github.com/ggml-org/llama.cpp
cd llama.cpp
cmake -B build -DGGML_HIP=ON \
  -DAMDGPU_TARGETS="gfx1150;gfx1102" \
  -DCMAKE_BUILD_TYPE=Release
cmake --build build --config Release -j
```

The `AMDGPU_TARGETS` list is the part that matters. You're telling the HIP compiler to emit code for both the iGPU and the dGPU in the same binary so you can switch between them with an environment variable. Build time is around 6 minutes on this machine. The resulting `build/bin/llama-server` is the binary you actually care about.

## The benchmark

The model is GLM-4 9B Q8_0 — Zhipu AI's 9B-parameter Chinese-and-English instruction-tuned model, quantized to 8-bit. It is, in my testing, the best open model under 10B for tool-calling and structured output as of April 2026. Llama 3.3 8B and Qwen 3 8B are close on raw reasoning; GLM-4 wins on instruction adherence inside agentic loops, which is the metric that matters here.

```bash
# Pin to the iGPU so the benchmark is honest about what Strix Point can do
HIP_VISIBLE_DEVICES=0 \
./build/bin/llama-bench \
  -m models/glm-4-9b-chat.Q8_0.gguf \
  -p 512 -n 256 -t 8 \
  -ngl 99
```

The relevant line from the output:

```
| model         | size   | params | backend | ngl | test  |          t/s |
| GLM-4 9B Q8_0 | 9.5 GB | 9.4 B  |   ROCm  |  99 |  tg256| 28.42 ± 0.31 |
```

**28.4 tokens/sec, sustained, on the iGPU alone.** Prompt processing (`pp512`) is faster — around 340 t/s — which matters because most agentic turns are heavy on prompt and light on generation.

For comparison, the same model at Q8_0 on:

| Hardware                    | tg t/s | Cost / month |
|-----------------------------|--------|--------------|
| Strix Point iGPU (this rig) |  28.4  | $0 (owned)   |
| RX 7700S dGPU (8GB)         |  ~35   | (offload only)|
| RTX 4070 (12GB)             |  ~52   | $600+ card   |
| Mac Studio M3 Ultra (96GB)  |  ~42   | $4,800       |
| Cloud H100 (per hour)       | 180+   | $2.49/hr     |

The H100 is faster per second. It is not faster per dollar, and it is not faster per *retry attempt at 3 a.m. when you've already burned your daily budget*.

## The economic case

Here is the argument I keep making to founders: if your agentic workflow needs to run *unattended for hours*, the cost of cloud inference is not your AWS bill — it is your willingness to let the agent retry. Every retry is a tokens decision, and humans ration tokens like they ration calories: badly, and with consequences for the work.

Concrete math, based on a real agentic dev loop I ran last week:

- **Loop**: planner → 3 parallel research agents → critic → executor → verifier
- **Avg tokens per full loop**: 180,000 in, 12,000 out
- **Loops per hour during active development**: 8–12
- **Sustained dev session**: 4 hours

That's roughly **6M input tokens and 400k output tokens per session**. On Claude Sonnet 4: ~$22/session. On GPT-5 reasoning: more. Per developer, per day. The cost is real, but the *behavioral* cost is what kills the loop — you start trimming retries, you start running fewer parallel agents, you let the model "good enough" instead of letting the critic loop converge.

On this machine, that same session is electricity. ~65W under sustained load × 4 hours = 0.26 kWh × $0.13 = **$0.034**. Three cents. The agent runs all night because there is no reason it shouldn't.

## What this actually unlocks

The interesting consequence is not "I saved money on tokens." It is the *regime change* in how you design loops:

1. **Parallel agent fan-out becomes free.** Five $0.01 cloud agents and one $0.05 monolith are roughly the same. Five local agents and one local monolith are the same too — except the local fan-out finishes in parallel and the cloud one finishes when the rate limiter says so.
2. **The critic gets to be expensive.** When generation is free, you can spend three turns of the critic arguing with the executor before you commit. This is the single largest quality unlock in agentic design and it is paywalled by token cost on metered APIs.
3. **You can leave loops running.** A research agent that wakes up every 15 minutes to scrape, summarize, and update a vector store is a $300/month subscription on cloud APIs. Locally it is the same as leaving Slack open.
4. **Experiments stop being expensive.** "What if the planner ran twice and we picked the better plan?" becomes a one-line change instead of a budget meeting.

## The catch (be honest about this)

96GB on Strix Point does not give you GPT-5. You will not run a 200B-parameter MoE on this hardware. What you get is:

- 7B–14B models at Q5–Q8, comfortably, with full context (32k–128k depending on model).
- A 27B model (Gemma 3 27B, Qwen 3 32B) at Q4_K_M with effort.
- No frontier-class single-shot reasoning. The frontier models still earn their bill on the *hardest* problems.

The right pattern is hybrid: local for the 95% of agentic turns that are routing, summarizing, drafting, calling tools, and critiquing; frontier API for the 5% of turns where you genuinely need the smartest model in the world. A well-designed loop calls the frontier ~once per session, not 80 times.
