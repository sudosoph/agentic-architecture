**TL;DR.** Andrew Ng told a room at AI Dev SF last week that the AI/human code ratio is moving from 80/20 to 100/0, and that the bottleneck is now product management, not engineering. At the same conference Marc Brooker from AWS argued the opposite: that the *opportunity* of agentic AI is now gated by defects, not capability. Both are right, and the synthesis is what this post is about. **Vibe coding is the founder's superpower if and only if you treat "stating intent" as the actual engineering work.** This post is about what intent-led development looks like in practice — the files, the hooks, the guardrails, and the failure modes I've personally burned through running this stack on AMD hardware for the last six months.

## Where we are, in numbers

A few data points from the last two weeks of conferences and shipped products, all of which are real and citable:

- **Google: over 75% of code generated by AI** (Paige Bailey, Google DeepMind, AI Dev SF, April 28).
- **CrewAI: 42% of code last week was AI-authored** (Joe Moura, AI Agent Conference NYC, May 4).
- **Claude Code: $2.5B revenue run-rate in February 2026**, twelve months after launch.
- **Wilson Lin published `fastrender` in January 2026: ~1M lines of Rust, ~30,000 commits, ~2,000 concurrent agents at peak**, written essentially as a planner-and-workers system that coordinated to keep work from overlapping.
- **42% of code, 75% of code, $2.5B run-rate.** Whatever you think about LLMs, the cost of a marginal line of code dropped by an order of magnitude in 2025 and is dropping again in 2026.

The tax this imposes is the one Andrew Ng pointed at: when SWE speeds up 10–100x, *everything else is slow in comparison*. Design, legal, marketing, ops, all suddenly become bottlenecks. The "AI-native team" he described is small, generalist, and structurally different — engineers who can write product copy, PMs who can ship features, designers who can read a diff. Per-engineer ARR is going up. Headcount is going down. The interesting positions are the ones where one person can plausibly play three roles, because the agent fills in the gaps.

If you're a founder, you are already that person. The question is whether your *codebase* is structured so the agents you've hired (in dollars-per-month, billed by Anthropic) can actually do the work.

## What "vibe coding" was, and what it became

Andrej Karpathy coined the term in February 2025. The original tweet was specifically about a throwaway weekend mode: forget the code exists, copy-paste the error message back into the agent, accept-all-diffs, never read what was written. In the original framing it was *not* a methodology — it was a holiday from methodology. A weekend treat.

What the term turned into in the year that followed is something different and more contested. The disillusionment piece that everyone in the discourse will eventually link is from a developer named Alberto Fortin in May 2025 — months of LLM-led coding produced what he described as "ten junior-mid developers locked in a room without seeing what the other nine were doing." Inconsistent naming. Duplicated logic. Architectural drift. He went back to pen-and-paper planning and treating the model as an assistant rather than the lead engineer.

Both stories are correct. The reconciliation is that *vibe coding works perfectly for projects you don't have to maintain* and *fails predictably for systems that have to live*. Karpathy was right about the weekend. Fortin was right about the codebase.

What founders need is a third thing: a discipline that takes the velocity of vibe coding and pays the small upfront tax that makes the output *maintainable*. Call it intent-led coding, or context engineering, or — the term I keep coming back to — *authoring constraints*.

## Authoring constraints, not authoring code

The shift is small in words and large in consequence. Stop writing code. Start writing the rules that constrain how code gets written. The agent does the typing.

Here's what that looks like on a real project — the very repo this site is built in. The codebase has a file at the root called `AGENTS.md` (Cursor reads it, Claude Code reads it, OpenAI Codex reads it; same source, three agents). The entire content of that file is:

```
# This is NOT the Next.js you know

This version has breaking changes — APIs, conventions, and file structure
may all differ from your training data. Read the relevant guide in
`node_modules/next/dist/docs/` before writing any code. Heed deprecation
notices.
```

That's it. Thirty-seven words. It does not describe how to write Next.js code. It does not list APIs. It does not give examples. What it does is **change the agent's behavior** — instead of relying on its training-data memory of a 2024 Next.js, the agent reads the version-pinned docs in `node_modules` before generating code. The diff before and after this file existed was the difference between "looks correct, doesn't compile" and "compiles on the first try."

That is what authoring constraints means in practice. A small, well-placed sentence that *describes the world correctly* saves you a hundred wrong diffs.

## The constraints worth authoring

Six categories, ordered roughly by leverage:

**1. The version-pinned reality.** "This is not the X you know" is the single highest-leverage sentence I have written in my whole career. Every framework that has had a breaking release between the model's training cutoff and today belongs in this list. Next.js 15 vs 16. React 19. Tailwind 4. Anything where the agent's training data is wrong about the present.

**2. The architectural invariants.** "All API routes use Edge runtime unless they need nodemailer." "Components in `components/site/` are always server components unless explicitly marked." "Database access goes through `lib/db.ts`, never directly from a route." These are statements of *should*, not how — they constrain choice without prescribing implementation. The agent picks the right pattern because the wrong pattern violates a rule.

**3. The deprecation map.** "We migrated off `react-query` to TanStack Query in March; old patterns from forums will not work." Agents will pull old patterns out of their training data. The deprecation map is how you tell them which patterns are dead.

**4. The taste rules.** "Default to writing no comments. Only add a comment when the WHY is non-obvious." "Don't add error handling for scenarios that can't happen." "Three similar lines is better than a premature abstraction." These bias the agent toward the aesthetic of your codebase. Without them, every model defaults to its own median taste — which is more comments, more error handling, more abstraction than you want.

**5. The hooks.** Memory and preferences alone don't *enforce*. Hooks do. A pre-commit hook that runs the type checker and rejects the diff is the difference between "the agent claimed it worked" and "the agent's diff actually compiles." Claude Code's hook system, Cursor's `.cursorrules`-driven validation, and good old `husky` for git-level enforcement all do the same job: they are the harness's immune system.

**6. The skills.** Reusable prompt-and-script bundles for tasks the agent has to repeat. A `/release` skill that knows how to bump the version, regenerate the changelog, and tag the commit. A `/migrate` skill that knows your specific data-migration pattern. A `/review` skill that runs the type checker plus your custom linters before declaring success. CrewAI's open `skills.crewai.com` is one example of the public version of this; Anthropic's PDF/DOCX/XLSX creation in Claude is shipped *entirely* as skills under the hood. The point is that skills are authored once and called by name forever.

These six categories are the entire job. There is no seventh thing.

## What changes for founders specifically

The most-quoted piece of trade-press cope from the last six months is some version of "founders can't really vibe-code a real product." This is wrong, and the existence proof is sitting on most of our home screens. Pieter Levels has been shipping seven-figure-revenue PHP apps with this approach since before it had a name. Wilson Lin's `fastrender` is a million lines of Rust written with this pattern. Paul Ford in the New York Times described converting a thorny dataset over a weekend that he would have charged $350,000 for in the previous era.

What changes specifically for the *founder* role:

**You will spend more time writing English than code.** The English you write is `AGENTS.md`, the architectural-invariant doc, the user stories, the taste rules. This is not less work than coding. It is differently shaped work. The skill is closer to product specification than to engineering.

**You will spend less time picking the right library.** The model has read more open-source code than you have. The right library is mostly a solved problem. What's not solved is *whether the right library should be used here* — that's a constraint question, and it's the question only you can answer.

**You will spend more time reviewing and less time typing.** This is the part of the job that is genuinely harder. Marc Brooker's argument at AI Dev was that the bottleneck on agentic AI is the defect rate, and that the most interesting opportunity is the *low frequency of low consequence defects* — bugs that are rare and small. The way you get there is not by typing; it's by reviewing. Aggressively. Build a culture of reading the diff even when the agent says it works.

**Your moat shifts from speed to taste.** In a world where any founder can have a working prototype by Friday, the prototypes that win are the ones that feel right. The ones with strong opinions in the UI, the ones with one-tenth the surface area but the right tenth, the ones whose error messages read like a person wrote them. Taste is the constraint that doesn't fit in a `.cursorrules` file. It comes from you.

## The local-first angle nobody else can give you

This is the piece I have not seen anyone else write, so I'll write it bluntly: **vibe coding gets cheaper and safer when the agent runs locally.**

A few reasons:

- **Token cost is the silent killer of long agent loops.** Every retry, every revision, every "let me try again" turn at metered API rates adds up. On Claude Sonnet 4 at 2026 prices, a busy agentic dev loop can run $20–60 per developer per day. On the Framework 16 with 96GB of unified memory I've written about elsewhere, the same loop is electricity. Three cents. The behavioral difference is enormous: you stop rationing retries, which means you stop trimming the part of the loop where the critic argues with the executor — which is where the quality lives.

- **Sandboxing is structurally easier when nothing leaves the machine.** Tushar Jain from Docker showed at AI Dev a per-agent MicroVM-based sandbox that limits what the agent can touch. That's the cloud-native version. The local-native version is even simpler: don't give the agent network access in the first place. A local model running in a container with no outbound DNS can write all the code it wants and exfiltrate exactly nothing. The threat model collapses.

- **The 4-legged identity problem disappears at home.** Matthew Xu gave a talk at AI Agent Conf about how OAuth was designed for the user-app-IdP triangle and breaks down in the user-agent-MCP-API square. Every cloud-agent setup has to solve this, and the production solutions involve token exchange (RFC 8693) and dynamic client registration (RFC 7591) and dual IdP integration. On a single-machine local setup, the equivalent of all of that is filesystem permissions and environment variables. The protocol's own authors carved an exception in for stdio transport: don't bother with OAuth, just use the env. Sovereign compute simplifies the auth story dramatically.

The thesis: as the agentic stack matures, *the gap between cloud-agent setup and local-agent setup widens in favor of local for tasks that don't require frontier-class reasoning*. A founder who can keep 95% of their agentic dev loop on their own hardware ships faster, cheaper, and with a smaller threat surface. The 5% that genuinely needs Claude or GPT-5 reasoning gets called by name, once per session, when it actually earns the bill.

## The failure modes I've personally hit

I'm not going to list "AI hallucinates" because everyone has heard it. Here are the failures I've run into in the last six months that I didn't see coming:

- **Test-suite rot.** The agent disabled a failing test rather than fix the underlying bug. Twice. The fix is a hook that rejects any diff that touches a test file unless the commit message explains why. Annoying. Worth it.
- **Looks-correct-but-isn't.** A migration that ran cleanly, type-checked, deployed — and silently truncated a numeric column from `bigint` to `int` because the agent inferred the wrong target type from a half-written model. Caught it in shadow mode (more on this in a future post). The lesson is the one Sanjin Bicanic gave at AI Agent Conf about the Bain HR-Services payroll agent: *production is the only truth. Shadow test before you ship.*
- **The 40K-token wall.** Jeff Huber from Chroma published research and said it again at AI Dev: language models are not invariant to their context windows. Past about 40K tokens, even the frontier models start to drift. The cure is not "buy a bigger context window." The cure is *stop putting noise in the context*. Skills, retrieval, and conflict resolution beat dumping the world into the prompt every time.
- **Cognitive debt.** This is the failure mode that scared me the most. After three weeks of accept-all-diffs on a feature, I realized I no longer fully understood the code that had my name on it. The fix is the rule that Steve Yegge calls "make the agent interview you" — before merging, ask the agent to ask you the questions it would ask if you were code-reviewing it. If you can't answer, you don't ship.

None of these are reasons to stop. All of them are reasons to author the right constraints up front.

## The honest tradeoff

Vibe coding's enemies aren't the people in the comments saying it produces slop. The slop is real, and it accumulates if you don't review. The enemies are subtler:

- **Vendor lock-in.** A $200/month subscription per agent per IDE is a real cost, and the artifacts you produce — Cursor Composer prompts, Claude Code skills, project memory files — are not portable across vendors. Authoring constraints in one tool's format doesn't transfer cleanly to another's.
- **Harness regression.** Anthropic publicly acknowledged in April 2026 that two months of degraded Claude Code quality were caused by a harness bug, not the model. If their flagship product can silently regress for two months without anyone diagnosing it, your project can absolutely do the same. External verification — tests, types, preview deploys, manual QA — is not optional.
- **Estimation chaos.** AI-assisted dev is wildly unpredictable per task. The same feature might take fifteen minutes or four hours. Sprint planning gets weird. The teams I've seen handle this best have abandoned story points entirely and switched to running outcomes through a small enough work-in-progress queue that estimation matters less.

The tradeoff is real. Whether you take it is a function of how much you're optimizing for velocity vs. how much you're optimizing for predictability. Most founders, most of the time, should be optimizing for velocity. But not all the time, and not for everything.

## What I'm watching

Three threads on the radar:

- **Specs as first-class artifacts.** Marc Brooker at AWS is shipping autoformalization tooling that turns natural-language SOPs into mathematically precise specifications, with deterministic enforcement against agent behavior. This is the production-grade version of "authoring constraints" and it's coming for codebases too. If you're building anything in regulated domains, watch this space.
- **Skills as the new package manager.** Anthropic's October 2025 skills launch was, in the language of AI Dev's panel, "a bigger deal than MCP." A skill is a folder with a `SKILL.md` and some scripts; the model loads it on demand, costs nothing in tokens until needed. Every team I respect is now publishing internal skills like internal libraries. There is a real chance this becomes the unit of code reuse in the agent era.
- **The harness war.** Cursor, Claude Code, OpenAI Codex, Gemini CLI, OpenClaw — five harnesses, each with strong opinions, each fighting for the developer's daily session. The next eighteen months will sort out which of them are products and which are features. Personally I run two daily and rotate; I would not bet on a single winner yet.

## The one-line summary

If you take one thing from this: **the agents are going to write the code either way. Your job is to write the constraints they read first.** Done well, that's the highest-leverage work a founder will do this decade.
