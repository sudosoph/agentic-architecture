The most profitable production AI architecture is not picking the single cheapest model and hoping users do not notice. It is a **three-tier routing pipeline** where a tiny sub-50ms classifier inspects each request, sends eighty to ninety percent of routine work to permissive open-weight workhorses (`Qwen 3.8-27B`, `Gemma 4`, `DeepSeek V4.1 Flash`), and escalates the genuinely hard five to fifteen percent to a flagship frontier model.

Because every major inference server (`vLLM`, `SGLang`, `llama-server`, `OpenRouter`) speaks the same OpenAI-compatible `/v1/chat/completions` contract, wiring this cascade takes less than fifty lines of code.

## The three-tier routing architecture

| Tier | Responsibility | Latency Target | Representative Models | Why It Works |
|---|---|---|---|---|
| **T0 · Classifier** | Intent bucket, complexity score, PII screen, cache key | `<= 50 ms` | `ModernBERT`, `Qwen 1.7B / 4B` | Costs fractions of a cent per 1,000 calls; never use a frontier model just to route |
| **T1 · Workhorse** | 80%-90% of turns: code edits, JSON extraction, routine drafts | `<= 1.5 s` TTFT | `Qwen 3.8-27B` (Apache 2.0), `DeepSeek V4.1 Flash` (MIT) | Fits on 24GB-128GB unified memory or low-cost hosted endpoints with constrained JSON decoding |
| **T2 · Escalation** | 5%-15% tail: cross-system debugging, legal/board synthesis | Deliberate | `Claude Sonnet/Opus`, `Gemini 4 Neon/Carbon`, `Kimi K3.1 Pro` | Reserves premium reasoning strictly for high-ambiguity or high-blast-radius turns |

## Six named routing recipes

### Recipe 1 · The Agentic Coding Loop
Fine-tune or prompt a `4B` router to label turns across `edit`, `explain`, `test_scaffold`, and `escalate`. Route `edit` and `test_scaffold` to `Qwen 3.8-27B` inside an isolated worktree gated by `tsc` and `vitest` ([see Loop Engineering](/blog/loop-engineering)), escalating only when deterministic checks fail twice or cross-service architecture is touched.

### Recipe 2 · High-Volume Support & Intake Triage
Classify inbound tickets by intent, urgency, and account tier in under 30ms with `ModernBERT`. Draft standard scheduling, documentation, and status replies on a fast MoE worker staged in Drafts, while routing billing disputes, legal notices, and enterprise escalations straight to Tier 2 plus a senior human owner.

### Recipe 3 · Constrained-Grammar Document Extraction
Pair layout-aware OCR ([see Document OCR for Agents](/blog/document-ocr-for-agents)) with `vLLM` constrained JSON-schema decoding on `Qwen 3.8-27B`. Grammar constraints force emitted tokens to conform to your target schema, Reserve 1M-context frontier endpoints strictly for 200-page packets or double validation failures.

### Recipe 4 · Overnight Research & Signal Sweeps
Use a small planner prompt to emit `{ search_queries, extraction_schema }`, run parallel retrieval and extraction locally or on cheap batch endpoints, and call a frontier synthesizer once at the end to reconcile contradictions ([see Automated Competitive Intelligence](/blog/automated-competitive-intelligence)).

### Recipe 5 · Speculative Decoding (`EAGLE-3`) for Latency-Critical UX
When single-model consistency is required, pair your `27B` target model with a `1.7B` speculative draft head in `vLLM`:

```bash
vllm serve Qwen/Qwen3.8-27B \
  --speculative-config '{"method":"eagle3","model":"Qwen/Qwen3-1.7B","num_speculative_tokens":5}' \
  --max-model-len 131072
```

Because rejected draft tokens are resampled from the target distribution, output quality remains mathematically identical while decode throughput jumps 2x to 3x.

### Recipe 6 · Diverse Mixture-of-Agents Committee for High-Stakes Review
For sensitive contract or clinical summaries, generate independent first-pass extractions across two distinct open-weight families (avoiding correlated single-checkpoint blind spots) and have a Tier-2 judge reconcile discrepancies and flag unverified spans.

## Minimal Python router with provider fallback

```python
decision = router.classify(prompt)  # "fast" | "workhorse" | "escalate"

if decision == "escalate":
    return frontier_client.chat(prompt, model="claude-sonnet")
if decision == "workhorse":
    return worker_client.chat(prompt, model="qwen-3.8-27b", response_format=schema)
return fast_client.chat(prompt, model="deepseek-v4.1-flash")
```

## Five cases where you should NOT mix models

1. **Low daily volume (`< 1M` tokens/day):** Engineering maintenance costs more than the API delta; stick to one strong model until volume grows.
2. **Uniformly hard reasoning:** If every single turn requires deep cross-domain synthesis, a router adds latency without savings.
3. **Single-voice conversational UX:** Switching models mid-dialogue creates subtle tone shifts unless normalized downstream.
4. **Strict single-checkpoint regulatory audits:** Certain compliance regimes require pinning one exact model version per validated pipeline.
5. **Unconstrained tool-call JSON:** Never route tool calls to smaller models without strict grammar/schema validation.
